## Execution Rules
- When running shell commands, always set `login: false`.
- Always run commands from the project root unless stated otherwise.
- Never hardcode, guess, or fabricate database credentials. If credentials are
  needed, read them from `web/sites/default/settings.php`.
- Ask for sensible class names, module names, and target locations **before**
  creating any file.
- Do not edit anything under `vendor/` directly — use Composer.
- After any code creation or modification, run `vendor/bin/grumphp run` before
  committing.

## Project Structure

```
project-root/
  web/                  <- Drupal docroot
    core/               <- Drupal core (never edit)
    modules/
      contrib/          <- Composer-managed contrib (never edit)
      custom/           <- All custom module code
    themes/
      contrib/          <- Composer-managed contrib (never edit)
      custom/           <- All custom theme code
    profiles/custom/    <- Custom install profiles
    sites/default/
      settings.php      <- Main config (no secrets committed)
      settings.local.php<- Local overrides (gitignored)
      files/            <- User-uploaded files (gitignored)
  config/               <- Exported configuration — source of truth
  drush/                <- Drush aliases and site config
  scripts/              <- Project utility scripts
  vendor/               <- Composer-managed PHP dependencies
  .env                  <- Local secrets (gitignored — copy from .env.example)
  composer.json
  phpunit.xml           <- PHPUnit config (gitignored if it has local paths)
  grumphp.yml           <- Generated by Drupal Guardrails
  phpstan.neon          <- Generated by Drupal Guardrails
  psalm.xml             <- Generated by Drupal Guardrails
  phpcs.xml.dist        <- Generated by Drupal Guardrails
```

**Key rules:**
- `config/` is source of truth — export after any config change:
  `vendor/bin/drush config:export`
- Production code lives in `web/modules/custom` and
  `web/themes/custom` only.
- Place service classes in a `services/` subdirectory within the module
  (e.g., `src/services/`).

## Coding Style & Standards

- Follow `.editorconfig`: 2-space indent (4 spaces in composer files), LF, no trailing whitespace.
- Drupal coding standards (`Drupal`, `DrupalPractice`) enforced by `phpcs.xml.dist`.
- Drupal naming: `module_name.module`, `ModuleNameController.php`, `module_name.settings.yml`.
- PHPDoc required on all public methods: `@param`, `@return`, `@throws`.
- Twig: `{{ variable|e }}` for output, `{% %}` for logic. Never use `|raw` on untrusted values.

## Security & Configuration Guidelines

### Secrets & Credentials
- Copy `.env.example` to `.env` locally — `.env` is gitignored and never committed.
- For database credentials: read `web/sites/default/settings.php`. Do not
  fabricate or hardcode them in any file.
- `settings.local.php` holds local environment overrides (gitignored). Wire it in
  at the bottom of `settings.php`:
  ```php
  if (file_exists($app_root . '/' . $site_path . '/settings.local.php')) {
    include $app_root . '/' . $site_path . '/settings.local.php';
  }
  ```
  Typical local overrides:
  ```php
  // web/sites/default/settings.local.php  (never commit this file)
  $config['system.logging']['error_level'] = 'verbose';
  $config['system.performance']['css']['preprocess'] = FALSE;
  $config['system.performance']['js']['preprocess'] = FALSE;
  ```

### Trusted Host Configuration (Required)
Prevents HTTP host header attacks and Drupal security warnings:
```php
// In settings.php
$settings['trusted_host_patterns'] = [
  '^example\.com$',
  '^www\.example\.com$',
  '^localhost$',
];
```

### Drupal Security Patterns
- **Untrusted output** — use `#plain_text`, `Html::escape()`, or `$this->t()`.
- **Trusted HTML only** — use `#markup` (passes through `Xss::filterAdmin()`).
  Never pipe user-supplied values through `#markup`.
- **Twig** — always use `|e`. Never use `|raw` on untrusted content.
- **SQL** — use Entity Query or `\Drupal::database()->select()` with placeholders.
  Never interpolate variables into raw SQL strings.
- **CSRF** — `FormBase` manages tokens automatically. Do not add manual `#token`
  without a documented reason.
- **Access control** — every route needs `_permission`, `_role`, or a custom
  access callback. UI-only restrictions are not sufficient.
- **File uploads** — validate MIME type and size server-side.
- **`php:eval` safety** — the code argument to `vendor/bin/drush php:eval` must
  never contain user-supplied or externally-sourced strings. This is a code
  execution vector.

## Drupal Development Patterns

### Services & Dependency Injection
- Define services in `modulename.services.yml`.
- Inject via constructor in controllers, forms, and plugins.
- Avoid static `\Drupal::` calls in service/controller classes — use injected dependencies.
- Permitted in procedural hook implementations: `\Drupal::service()`.
- Place service classes in `src/services/` within the module.
- Discover available services:
  ```bash
  vendor/bin/drush eval "print_r(\Drupal::getContainer()->getServiceIds());"
  ```

### Entity API & Queries
- **Load single**: `\Drupal\node\Entity\Node::load($id)`
- **Load multiple**: `\Drupal::entityTypeManager()->getStorage('node')->loadMultiple($ids)`
- **Query**:
  ```php
  $ids = \Drupal::entityTypeManager()
    ->getStorage('node')
    ->getQuery()
    ->accessCheck(TRUE)
    ->condition('status', 1)
    ->execute();
  ```
  > `\Drupal::entityQuery()` was deprecated in Drupal 9.3 — do not use it.
- **Always call** `->accessCheck(TRUE)` unless you intentionally bypass access
  (document why if so).
- **Create**: `\Drupal\node\Entity\Node::create(['type' => 'article'])->save()`

### Plugin System
- Extend the correct base: `BlockBase`, `FormatterBase`, `WidgetBase`, `MenuLinkDefault`.
- Use annotation-based discovery (`@Block`, `@FieldFormatter`, etc.) in docblocks.
- Place plugins in `src/Plugin/<PluginType>/` within the module.

### Hooks
- Implement in `modulename.module`.
- Delegate complex logic to a service class — keep hooks thin.
- Common: `hook_form_alter()`, `hook_theme()`, `hook_entity_presave()`.
- Fire in module weight order (lowest weight first).

### Forms API
- Extend `FormBase` for standard forms, `ConfigFormBase` for configuration forms.
- Implement `buildForm()`, `validateForm()`, `submitForm()`.
- `FormBase` handles CSRF automatically — do not add `#token` without reason.
- Use `#plain_text` for user-supplied values in render arrays.

### Routes & Controllers
- Define in `modulename.routing.yml` with `path`, `defaults`, `requirements`.
- Controllers extend `ControllerBase`, live in `src/Controller/`.
- Every route must have an access check.
- Return render arrays or Symfony `Response` objects.

### Configuration Management
- `config/` is the source of truth — export after every config change.
- Read: `\Drupal::config('system.site')->get('name')`
- Write: `\Drupal::configFactory()->getEditable('system.site')->set('name', $val)->save()`

## Testing & Quality Assurance

### PHPUnit Setup
```bash
cp web/core/phpunit.xml.dist phpunit.xml
```
Configure in `phpunit.xml`:
- `SIMPLETEST_BASE_URL` — e.g., `http://127.0.0.1:8888`
- `SIMPLETEST_DB` — use SQLite locally (no credentials required):
  ```
  sqlite://localhost//tmp/drupal_test.sqlite
  ```
- `BROWSERTEST_OUTPUT_DIRECTORY` — writable path for functional test output

For MySQL/PostgreSQL test runs: read credentials from
`web/sites/default/settings.php` and construct the DSN — never hardcode
them. Do not commit `phpunit.xml` if it contains local paths.

### Test Types

**Unit** (`tests/src/Unit/`, extends `UnitTestCase`)
- No Drupal bootstrap — fastest
- Mock all external dependencies
- Use for: service logic, utility functions, calculations
- Name: `ThingUnitTest.php`

**Kernel** (`tests/src/Kernel/`, extends `KernelTestBase`)
- Partial bootstrap, in-memory SQLite database
- Declare modules in `$modules`
- Use for: entity CRUD, config validation, service registration
- Name: `ThingKernelTest.php`

**Functional** (`tests/src/Functional/`, extends `BrowserTestBase`)
- Full bootstrap, browser simulation
- Set `$defaultTheme` (use `'stark'`)
- Use for: form submissions, permissions, full user journeys
- Assertions via `$this->assertSession()`
- Name: `ThingFunctionalTest.php`

Target: **≥ 80% coverage** on custom modules.

## Troubleshooting

### Composer Memory Issues
```bash
# Increase limit — use as a last resort, not a default
php -d memory_limit=512M /usr/local/bin/composer install
# Avoid -1 (unlimited) — it can exhaust server RAM.
```

### File Permission Issues
```bash
chmod 755 web/sites/default/files
chmod 644 web/sites/default/settings.php
chown -R www-data:www-data web/sites/default/files
# Never use chmod 777 — it is a security risk.
```

### Database Connection Issues
1. Read `web/sites/default/settings.php` for the configured host and credentials.
2. Verify the DB service is running: `systemctl status mysql` or `systemctl status postgresql`
3. Run `vendor/bin/drush status` and check the Database row.
4. Check: `vendor/bin/drush watchdog:show --type=php --severity=Error`

### Module/Theme Issues
```bash
vendor/bin/drush cr                              # Always try this first
vendor/bin/drush config:get core.extension       # Verify module is registered
vendor/bin/drush twig:debug on && vendor/bin/drush cr  # Enable template debugging
# Check HTML source for <!-- THEME DEBUG --> comments
```

### Config Conflicts After Pull
```bash
vendor/bin/drush config:diff
vendor/bin/drush config:import
vendor/bin/drush updatedb
vendor/bin/drush cr
```

### Testing Issues
```bash
# Missing phpunit.xml
cp web/core/phpunit.xml.dist phpunit.xml
# Set SIMPLETEST_BASE_URL and SIMPLETEST_DB — use SQLite for local runs
# Read settings.php for MySQL/PostgreSQL credentials — do not hardcode them
```

## Advanced Patterns

### Batch API
For large datasets that would hit PHP timeouts:
- Define a batch array: `title`, `operations` (array of callables + args), `finished` callback.
- Process in chunks to prevent memory exhaustion.
- Drupal renders a progress bar automatically.

### Queue API
For background processing that should not block requests:
- Add: `\Drupal::queue('queue_name')->createItem($data)`
- Process via `QueueWorker` plugin (`src/Plugin/QueueWorker/`) on cron.
- Failed items can be released back to the queue.

### AJAX Forms
- Add `#ajax` property: `callback`, `wrapper` (target element ID), `event`.
- Return a render array from the callback.
- Use `$form_state->getTriggeringElement()` to identify the triggering element.
- Wrap callbacks in try/catch and return `AjaxResponse` with commands on error.
